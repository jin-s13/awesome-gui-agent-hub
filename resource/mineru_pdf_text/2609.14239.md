## Abstract

Static benchmarks for computer-use agents fix a task set at release and score every system against it once. That makes them reproducible, and it lets them drift from what they should measure: a fixed task set ages, leaks into training corpora, and cannot follow how people actually use agents from week to week. CoArena measures use directly. Real users submit tasks; two systems, each a single model or a multi-agent pipeline behind the same tool interface, execute the same task concurrently in identical sandboxed desktops; users judge the two outcomes without knowing which system produced them; and a public leaderboard is refit from those judgments. The central contribution is a formal account of what makes such an evaluation real-time. We define real-time as five measurable properties, each with an equation and a worked example: continuous task arrival, live concurrent execution, online rating updates, freshness with contamination resistance, and bounded feedback latency from a failed run to a reusable training environment. The rating methodology follows in full: the Bradley-Terry pairwise model, its likelihood with weighted observations and ties, the penalized maximum-likelihood estimator, and the streaming update applied when a single vote arrives (a stochastic-gradient step on the same likelihood, recovering Elo). It gives confidence intervals from the observed information and a cluster-robust sandwich, rank bands from a parametric bootstrap, the rule by which a new system enters the board, and the convergence rate of the estimate. Vote quality is treated with inter-judge agreement statistics, redundant judging, and explicit handling of ties and abstentions. A five-system example with 211 votes is carried from the vote matrix to ratings, intervals, and rank bands. Every number is derived from stated inputs or labeled illustrative; none is a measurement of a deployed system.

## 1 Introduction

A computer-use agent receives an instruction in natural language and operates a desktop or a browser on a person’s behalf: it reads the screen, moves a pointer, types, and delivers a result. The agent may be a single model behind a fixed scafold, or a multi-agent system that plans, delegates and verifies internally before it acts. From the outside the two look the same, an instruction goes in and actions on a screen come out, and they can be evaluated the same way. So far that evaluation has followed the pattern set for language models: a benchmark author writes a fixed set of tasks, each with a programmatic or rubric-based checker, and every system is scored against that set [6, 18, 30, 33]. The pattern has one clear virtue, reproducibility, and three structural weaknesses when the object of study is a system people actually use.

First, a fixed task set does not track use. The distribution of tasks people ask agents to do shifts with the software they use, the sites they visit, and the agents’ own growing capabilities. A benchmark frozen in one year measures the workload of that year.

Second, a fixed task set ages into the training data of the models it is meant to measure. The concern is documented for language benchmarks [14, 27] and has motivated benchmarks that refresh their questions on a schedule [15, 29]. A scheduled refresh reduces the problem; i does not remove the interval during which a released task set is both public and in use.

Third, a fixed task set is scored by a checker written in advance, and the checker encodes the author’s notion of success. For open-ended computer work, whether an outcome is acceptable often depends on the person who asked. Human preference between two attempts at the same task is a diferent measurement, one that pairwise arenas for chatbots have collected at scale [3, 32].

This paper describes an arena for computer-use agents built around those three observations, and it makes one claim precise: that the arena is a real-time evaluation. The word is used loosely across evaluation platforms. We define it as a set of five measurable properties (Section 4), each with notation, an equation where one applies, and a worked example. The properties are continuous task arrival, live concurrent execution, online rating updates, freshness with contamination resistance, and bounded feedback latency from a failed run to a reusable training environment. Continuous arrival means the evaluation has no release epochs. Live concurrent execution means that both agents run the same task at the same time in identical environments, and that execution is contemporaneous with submission. Online rating updates means that the published rating is a bounded-latency function of every admissible judgment. Freshness means that a task is executed within minutes of being written, before any training pipeline can have observed it. Bounded feedback latency means that a failure becomes something a developer can train against within a stated horizon.

The rest of the paper supplies the machinery those properties rest on. Section 3 describes the arena concretely. Section 5 presents the rating methodology: the pairwise model, its likelihood, the batch and streaming estimators, intervals, rank bands, entry of new agents, and convergence. Section 6 carries a small example through the whole pipeline and treats vote quality. Sections 7 and 8 discuss limitations and conclude. Appendix A collects the notation (Table 3), Appendix B lists the algorithms (Algorithms 1 to 4), and Appendix C walks one battle through the interfaces.

A note on numbers. Every number in this paper is either derived from stated inputs in the text, produced by a simulation whose generative model and seed are stated, or labeled as illustrative. None is a measurement of a deployed system, and the reader should not interpret any figure here as an empirical result about a particular product.

## 2 Related Work

Paired-comparison models. The model we use for ratings originates with Zermelo’s treatment of chess tournament results [31] and was developed independently by Bradley and Terry [2]. Ford gave the condition under which the maximum-likelihood estimate exists: the comparison graph must be strongly connected in the sense that every agent has both a win and a loss path to every other [10]. Hunter analyzed minorization-maximization algorithms for the model and its generalizations [13]; Newman gave an accelerated iteration [24]. Ties were incorporated by Rao and Kupper through a threshold parameter [25] and by Davidson through a separate tie propensity [5]. The Elo rating system [8] is the sequential update familiar from chess rating; Glickman’s Glicko [11] and the TrueSkill system [12] add a per-player uncertainty that widens with inactivity.

Arenas for language models. Chatbot Arena collected human pairwise preferences between anonymized chatbots and fit a Bradley-Terry model to them, with bootstrap confidence intervals [3, 32]. Its authors and others have examined the robustness of Elo-style ratings to vote order and sample size [1] and the influence of response style on human preference [20]. Our setting difers in what is compared (a trajectory of screen actions ending in a delivered result, rather than a text response) and in the cost of a comparison (minutes of sandboxed execution rather than a single generation), which shapes the concurrency and queueing analysis of Section 4.

Benchmarks for computer-use agents. OSWorld [30], WebArena [33], VisualWebArena [18], Mind2Web [6], and Android in the Wild [26] established executable environments with fixed task sets and programmatic checkers. They remain the appropriate instrument when reproducibility of a specific task is the goal. Our arena is complementary: its tasks are whatever users submit, its judgments are human, and its purpose is to track use rather than to fix a target.

Contamination and refreshed benchmarks. The leakage of evaluation data into training corpora has been measured for language benchmarks [27], and mitigations range from withholding test data from plain-text distribution [14] to periodic refresh [15, 29] to adversarial, human-in the-loop data collection [16]. We treat contamination resistance as a consequence of the arrival process: a task that is written and executed within minutes cannot have been in any training set that closed before it was written (Property 4).

Uncertainty in evaluation. Cluster-robust variance estimation [21, 28] and the bootstrap [7] are the tools we use for intervals, following the argument that evaluation results should carry error bars that account for the dependence structure of the data [23].

## 3 System Design

This section describes the arena concretely. Figure 1 shows the components; Figure 2 shows one task’s passage through them.

## 3.1 Participants and objects

The arena has a roster of agents $\mathcal { A } , \vert \mathcal { A } \vert = m$ . An agent is whatever sits behind the arena’s fixed tool interface and turns an instruction into actions on the desktop: a single model under the arena’s own scafold (tool set, system prompt, step budget), or a multi-agent system with its own planner, workers and verifier that the arena drives through the same interface and treats as one entrant. The arena sees only the actions and the delivered result, so a single model and a multi-agent system are rated by the same rule and can be compared on the same board. Users submit tasks. A task τ is a natural-language instruction, optional file attachments, and an optional starting URL. A battle b pairs one task with two distinct agents $a , a ^ { \prime } \in { \mathcal { A } }$ and produces two runs, one per agent. A judgment is a user’s blind choice between the two runs of a battle.

## 3.2 Intake

Every task enters through one endpoint. The endpoint authenticates the submitter, checks that the submitter’s consent to publication is current, classifies the message as a task (which will boot two sandboxes) or as conversational text that should not, applies a near-duplicate guard against the submitter’s recent tasks, and admits the task to a bounded queue. Admission is deliberately wider than execution so that a burst of submissions becomes waiting time rather than an error.

## 3.3 Matchmaking

The two agents for a battle are drawn by a sampler that depends only on the roster, the count of rated battles each agent has accumulated, and the current ratings. It depends on nothing the submitter supplies. Three properties are enforced by construction and are stated here because they matter for the rating analysis. Every eligible agent has a strictly positive probability in every draw, so no agent can be starved. Agents with fewer rated battles are sampled more often, with weight proportional to $( n _ { a } + \kappa ) ^ { - 1 / 2 }$ for a pseudo-count $\kappa > 0$ , so that measurement converges toward equal exposure. Among opponents, pairs whose outcome is uncertain under the current ratings are preferred, because those comparisons carry more information about the parameters (Section 5.8).

## 3.4 Execution

Each run executes in its own sandboxed desktop environment: an isolated virtual machine with a display, a browser, and a shell, provisioned fresh for the run. The two runs of a battle are provisioned and started together, receive byte-identical inputs (instruction, attachments, tool schemas, step budget, wall-clock budget), and execute concurrently. An agent acts through a fixed tool set (pointer, keyboard, navigation, a screenshot on every step, and a bounded shell where the environment permits it) and may end its run by delivering files and a final message. Every step’s screenshot and action are recorded. Network egress from a sandbox is restricted to public destinations; private address ranges are blocked at the resolver and at the proxy.

## 3.5 Judging

When both runs have ended, the battle becomes available for judging. A judge sees the task, both trajectories as replays, and both final results, with the agents’ identities withheld by the server until the judge has voted. The judge chooses one side, declares a tie, declares both unacceptable, or abstains. A random fraction of battles, drawn at creation time, is assigned a redundancy target of three judges rather than one; this sample is what agreement statistics are computed from (Section 6.4). The submitter of a task may judge their own battle, blind like anyone else; the treatment of that vote is specified in Section 5.5.

## 3.6 Rating and leaderboard

Two estimators run. A streaming update adjusts the two agents’ ratings the moment a judgment resolves a battle (Algorithm 1). A batch estimator refits the pairwise model from every admissible judgment on a fixed period and is what the public leaderboard displays, together with confidence intervals and rank bands (Algorithms 2 and 3). Figure 3 shows, in a simulation, how the refit’s interval narrows as judgments accumulate, and Figure 4 shows a simulated day of arrivals and completed runs under the capacity model of Section 4.3. The leaderboard lists the roster only; an agent removed from the roster keeps its historical battles in the corpus, and they continue to inform the ratings of the agents it played, but it takes no position.

## 3.7 Failure to environment

A run that ends in failure (the agent gives up, the step or time budget is exhausted, or a checker judges the delivered result wrong) is a candidate for conversion into a training environment: a reproducible initial state, the instruction, and a grader derived from what went wrong (Figure 5). The conversion runs as a pipeline with a stated latency target (Property 5).

## 4 Formal Model of Real-Time Evaluation

This section is the paper’s central contribution. We give a formal setting, then define real-time as five properties. Each property has notation, a measurable quantity, an equation where one applies, and a worked numerical example with clearly labeled illustrative inputs. We close with a composite definition and a table of time-horizon tiers.

## 4.1 Setting and events

Let time be $t \in \mathbb { R } _ { \geq 0 }$ . Tasks arrive as a sequence $\tau _ { 1 } , \tau _ { 2 } , . . .$ . with submission times $s _ { 1 } < s _ { 2 } < \cdots$ The arrival counting process is

$$
N (t) = \# \{i: s _ {i} \leq t \}.\tag{1}
$$

Each task becomes one battle b with agents $( a _ { b } , a _ { b } ^ { \prime } )$ . For a battle we record the event times shown in Figure 2: submission $s _ { b } ;$ dequeue $q _ { b } .$ , when the orchestrator admits the battle to execution; lane start $q _ { b } + \delta _ { b }$ , where $\delta _ { b } \geq 0$ is provisioning time; execution end $e _ { b } ,$ , when both runs have ended; first admissible judgment $h _ { b } ;$ rating incorporation $r _ { b } .$ , the first time a published rating is a function of that judgment; and service $\ell _ { b }$ , the first time a client is served a leaderboard that reflects it. The corresponding latencies are

$$
L _ {b} ^ {\mathrm{q}} = q _ {b} - s _ {b}, \quad L _ {b} ^ {\mathrm{p}} = \delta_ {b}, \quad L _ {b} ^ {\mathrm{e}} = e _ {b} - (q _ {b} + \delta_ {b}), \quad J _ {b} = h _ {b} - e _ {b}, \quad L _ {b} ^ {\mathrm{r}} = r _ {b} - h _ {b}, \quad L _ {b} ^ {\mathrm{s}} = \ell_ {b} - r _ {b}.\tag{2}
$$

The end-to-end latency is their sum, $\ell _ { b } - s _ { b }$ . We separate the machine latency

$$
M _ {b} = L _ {b} ^ {\mathrm{q}} + L _ {b} ^ {\mathrm{p}} + L _ {b} ^ {\mathrm{e}} + L _ {b} ^ {\mathrm{r}} + L _ {b} ^ {\mathrm{s}}\tag{3}
$$

from the human latency $J _ { b } ,$ , because the system can bound the former and can only observe, sample, and prioritize the latter.

For a set of battles S and a latency $X _ { b } ,$ , we write $\bar { X } ( S )$ for the mean and $X _ { p } ( S )$ for the p-th percentile over S. Real-time properties are stated as bounds on percentiles, because a mean hides the tail that a user experiences.

## 4.2 Property 1: continuous task arrival

Property 1 (Continuous arrival) The evaluation has no release epochs. Formally, the arrival process N(t) has a strictly positive long-run rate

$$
\lambda = \lim _ {t \to \infty} \frac {N (t)}{t} > 0,\tag{4}
$$

and over any observation horizon [0, T] the largest gap between consecutive arrivals,

$$
G _ {\mathrm{max}} (T) = \max _ {i: s _ {i + 1} \leq T} (s _ {i + 1} - s _ {i}),\tag{5}
$$

is small relative to T. A batch benchmark violates the property in the strongest way: its $N ( t )$ is a step function with one jump per release, so $G _ { \mathrm { m a x } } ( T )$ equals the release interval.

The natural model for user submissions is a Poisson process [17], possibly with a time-varying rate λ(t) to capture diurnal patterns. If submissions follow a homogeneous Poisson process at rate λ, the gap between consecutive tasks has an exponential distribution with mean $1 / \lambda$ , and a window of length w stays empty with probability

$$
\mathbb {P} \{\text { no   arrival   in } w \} = e ^ {- \lambda w}.\tag{6}
$$

Worked example (illustrative inputs). Take λ = 12 tasks per hour. The mean gap is $1 / \lambda = 5$ minutes. The probability that a 30-minute window contains no task is e<sup>−</sup> $^ { - 1 2 { \cdot } 0 . 5 } = e ^ { - 6 } \approx$ 0.0025. Over a 24-hour horizon the expected count is λT = 288. Figure 4 shows one simulated day at this rate (280 arrivals in that draw).

## 4.3 Property 2: live concurrent execution

Property 2 (Live concurrent execution) Both runs of a battle execute at the same time, in isolated environments, on identical inputs, and execution is contemporaneous with submission. Formally: (i) parity: the resolved input tuple I(b) (instruction, attachments, tool schemas, step budget K, wall-clock budget W, environment image) is identical for both lanes; (ii) co-start: the two lane start times difer by at most a skew bound $\Delta _ { \mathrm { s t a r t } } ; ( i i i )$ isolation: the two environments share no mutable state during $[ q _ { b } , e _ { b } ] ;$ and (iv) contemporaneity: the machine latency to execution end is bounded at a stated percentile,

$$
\left(L ^ {\mathrm{q}} + L ^ {\mathrm{p}} + L ^ {\mathrm{e}}\right) _ {p} \leq H _ {\mathrm{exec}}.\tag{7}
$$

Parity is what makes a judgment a comparison of agents rather than of conditions. It is enforced by resolving every mutable input once per battle and handing the same objects to both lanes, and it is checked by a test suite rather than by review. Condition $( \mathrm { i v } )$ is the one that distinguishes a live arena from an evaluation that records tasks now and runs them later.

The bound in (7) is a capacity question. Let $C$ be the number of battles that may execute concurrently and let $S _ { b } = L _ { b } ^ { \mathrm { p } } + L _ { b } ^ { \mathrm { e } }$ be a battle’s service time, with mean $\mathbb { E } [ S ]$ . The ofered load is

$$
\rho = \frac {\lambda \mathbb {E} [ S ]}{C},\tag{8}
$$

and the queue is stable only if $\rho < 1$ . Little’s law [22] ties the wait to the load: the expected count of battles present, whether waiting or executing, is

$$
\mathbb {E} [ \mathrm{insystem} ] = \lambda (\mathbb {E} [ L ^ {\mathrm{q}} ] + \mathbb {E} [ S ]).\tag{9}
$$

Worked example (illustrative inputs). With $\lambda = 1 2$ per hour = 0.2 per minute, $\mathbb { E } [ S ] = 6 . 8$ minutes, and $C = 4$ , the load is $\rho = 0 . 2 \times 6 . 8 / 4 = 0 . 3 4$ . In the simulation of Figure 4, which uses a lognormal service time with median 6 minutes and log-scale standard deviation 0.5 (so $\mathbb { E } [ S ] = 6 e ^ { 0 . 1 2 5 } = 6 . 8 0$ minutes), the mean queue wait was 0.09 minutes and the largest wait was 2.87 minutes; by (9) the mean number in system is $0 . 2 \times ( 0 . 0 9 + 6 . 8 0 ) \approx 1 . 4$ battles. If λ doubled to 24 per hour at the same $C _ { i }$ , the load would be $\rho = 0 . 6 8$ and waits would grow sharply. The design response is to raise $C _ { i }$ , not to defer execution, because deferral breaks condition (iv).

## 4.4 Property 3: online rating updates

Property 3 (Online rating updates) The published rating at time t is a function of every admissible judgment made before $t - L ^ { \mathrm { r } }$ , for a bounded update latency $L ^ { \mathrm { r } }$ that does not grow with the size of the corpus. Define the staleness of the published rating at time t as

$\varsigma ( t ) = t - \operatorname* { m i n } \{ h _ { b } : h _ { b } \leq t ,$ , b is not yet reflected in the rating served at $t \}$ ,

(10)

with $\varsigma ( t ) = 0$ when no such judgment exists: the time the oldest unincorporated judgment has been waiting. A board with no pending judgment is current, however long ago the last vote arrived. The property requires su $\begin{array} { r } { \operatorname { l p } _ { t } \varsigma ( t ) \le H _ { \mathrm { r a t e } } } \end{array}$ for a stated horizon.

Two estimators satisfy this property in diferent ways (Section 5). The streaming update touches two parameters per judgment and has latency of milliseconds, but it depends on the order in which judgments arrived and cannot retroactively apply a retraction or a newly discovered exclusion. The batch refit is order-independent and applies every rule to the whole corpus, at the cost of a compute step. It runs on a fixed period $\Delta$ with compute time $c ,$ so its staleness is bounded by

$$
\varsigma (t) \leq \Delta + c.\tag{11}
$$

The arena publishes the refit as the rating and shows the streaming value beside it, labeled, because the streaming value is what a judge sees move when they vote.

Worked example (illustrative inputs). With $\Delta = 3 0 ~ \mathrm { : }$ s and $c = 1 ~ { \mathrm { s } } .$ , the served rating is never more than 31 s stale. A benchmark that republishes weekly has ς up to $7 \times 8 6 , 4 0 0 = 6 0 4 , 8 0 0$ s, a ratio of about $2 \times 1 0 ^ { 4 }$ . The streaming update, with a latency of the order of 10 ms, makes a judge’s own vote visible to that judge at once; the refit makes it part of the published number within $\Delta + c .$

## 4.5 Property 4: freshness and contamination resistance

Property 4 (Freshness and contamination resistance) A task is executed shortly after it is written, and before any agent’s training pipeline could have observed it. Define the task age at execution $A _ { b } = q _ { b } - s _ { b }$ and, for agent a with training-data cutof time $t _ { a } ^ { \mathrm { c u t } }$ , the contamination indicator

$$
c _ {b} = \mathbf {1} \left[ s _ {b} \leq \max _ {a \in \{a _ {b}, a _ {b} ^ {\prime} \}} t _ {a} ^ {\mathrm{cut}} \right],\tag{12}
$$

which is 1 exactly when the task existed before the later of the two agents’ cutofs. The property requires $( i ) ~ A _ { p } \leq H _ { \mathrm { a g e } }$ at a stated percentile and $( i i ) c _ { b } = 0$ for every rated battle. Because a task is written by its submitter at $s _ { b }$ and every deployed agent’s cutof precedes deployment, (ii) holds for the arriving stream by construction; the residual risk is a repeated task, one whose text near-duplicates an earlier public task, which is handled by the duplicate guard at intake and measured by a duplicate rate.

We measure freshness of the rating corpus itself by the share of rating weight that comes from tasks newer than an age α:

$$
F (\alpha ; t) = \frac {\sum_ {b : t - s _ {b} \leq \alpha} w _ {b}}{\sum_ {b} w _ {b}},\tag{13}
$$

where $w _ { b } \in ( 0 , 1 ]$ is the evidence weight of battle b in the likelihood (Section 5.5) and both sums run over the battles the rating is fitted on at time t. Under a constant arrival rate and a corpus window of the newest $N _ { w }$ battles with equal weights, $F ( \alpha ) = \operatorname* { m i n } \{ 1 , \lambda \alpha / N _ { w } \}$

The duplicate rate at threshold θ is

$$
D (\theta) = \frac {1}{| \mathcal {B} |} \sum_ {b} \mathbf {1} \left[ \max _ {b ^ {\prime}: s _ {b ^ {\prime}} <   s _ {b}} \mathrm{sim} (\tau_ {b}, \tau_ {b ^ {\prime}}) \geq \theta \right],\tag{14}
$$

where sim is a lexical similarity (we use word-trigram Jaccard) and B is the rated corpus. $D ( \theta )$ is a measured quantity of a deployed arena; in this paper we write it as a placeholder $D ( 0 . 5 5 ) = [ \mathrm { t o }$ be measured] rather than assert a value.

Worked example (illustrative inputs). If the machine stages of Figure 2 take $L ^ { \mathrm { q } } = 5$ s and $L ^ { \mathrm { p } } = 4 0 ~ \mathrm { s }$ , a task is under execution 45 s after it was written; no training pipeline with a cutof before $s _ { b }$ can contain it, so $c _ { b } = 0$ . With λ = 12 per hour = 288 per day and a fitting window of $N _ { w } = 2 0 \small { , } 0 0 0$ battles, the window spans $2 0 , 0 0 0 / 2 8 8 \approx 6 9$ days and the share of rating weight from the last 7 days is $F ( \mathrm { 7 d } ) = 2 8 8 \times 7 / 2 0 { , } 0 0 0 \approx 0 . 1 0 . \mathrm { ~ A }$ fixed benchmark released once has $F ( \alpha ) = 0$ for every α shorter than its age.

## 4.6 Property 5: bounded feedback latency to a training environment

Property 5 (Bounded feedback latency) A failed run becomes a reusable, validated training environment within a stated horizon. Let $\mathcal { F }$ be the set of runs whose outcome is a failure (the agent gave up, exhausted its budget, or delivered a result a checker rejects). For $u \in { \mathcal { F } }$ with end time $e _ { u } ,$ let $\varepsilon _ { u }$ be the derived environment and $\nu _ { u }$ the time it is published, validated, to the registry. The feedback latency is

$$
T _ {u} ^ {\mathrm{env}} = \nu_ {u} - e _ {u} = T _ {u} ^ {\mathrm{cap}} + T _ {u} ^ {\mathrm{red}} + T _ {u} ^ {\mathrm{syn}} + T _ {u} ^ {\mathrm{val}} + T _ {u} ^ {\mathrm{pub}},\tag{15}
$$

the sum of capture, redaction, synthesis, validation, and publication stage times (Figure $5 ;$ Algorithm $\it 4 )$ . The property requires $T _ { p } ^ { \mathrm { e n v } } \leq H _ { \mathrm { e n v } }$ at a stated percentile, and it requires reusability: $\varepsilon _ { u }$ must be reproducible from a stored initial state and a stored instruction, and validity: replaying the failing trajectory in $\varepsilon _ { u }$ must reproduce the failure, and a reference trajectory must pass the derived grader.

Validation runs the pipeline’s own replay twice, once with the failing trajectory and once with a reference, so $T ^ { \mathrm { v a l } }$ is at least two run durations.

Worked example (illustrative inputs). Take $T ^ { \mathrm { c a p } } = 2 0 ~ \mathrm { s } , ~ T ^ { \mathrm { r e d } } = 4 0 ~ \mathrm { s } , ~ T ^ { \mathrm { s y n } } = 3 0 0 ~ \mathrm { s } ,$ $T ^ { \mathrm { v a l } } = 2 \times 4 8 0 = 9 6 0 ~ \mathrm { s } ,$ and $T ^ { \mathrm { p u b } } = 1 0 ~ \mathrm { s }$ . Then $T ^ { \mathrm { e n v } } = 1 , 3 3 0 ~ \mathrm { s } \approx 2 2$ minutes, inside a one-hour horizon $H _ { \mathrm { e n v } } = 3 , 6 0 0 ~ \mathrm { s }$ . Validation dominates, and it scales with the run length, so an arena with a 20-minute wall-clock budget should expect $T ^ { \mathrm { e n v } }$ of the order of an hour at its tail.

## 4.7 Composite definition and time-horizon tiers

Definition 4.1 (Real-time arena evaluation at horizon H) An arena evaluation is realtime at machine horizon H and environment horizon $H _ { \mathrm { e n v . } }$ , at percentile $p ,$ if over its observation window:

1. (arrival) $\lambda > 0$ and $G _ { \operatorname* { m a x } } ( T ) \leq H$ for every horizon T of at least one day;

2. (execution) parity, co-start with $\Delta _ { \mathrm { s t a r t } } \ \leq \ H$ , and isolation hold for every battle, and $( L ^ { \mathrm { q } } + L ^ { \mathrm { p } } + L ^ { \mathrm { e } } ) _ { p } \leq H _ { \mathrm { \Omega } }$ .

3. (rating) $\operatorname { s u p } _ { t } \varsigma ( t ) \leq H$ ;

4. (freshness) $A _ { p } \leq H$ and $c _ { b } = 0$ for every rated battle;

5. (feedback) $T _ { p } ^ { \mathrm { e n v } } \leq H _ { \mathrm { e n v } }$ , with reusability and validity.

The human latency $J _ { b }$ is reported alongside, at the same percentile, and is not part of the definition, because it is the property of a population of judges rather than of the system.

Table 1 arranges horizons into tiers. An evaluation can be real-time at one tier for some properties and not others; the honest statement names the tier per property.

## 4.8 What the definition excludes

Three designs are sometimes described as real-time and fail Definition 4.1. A benchmark refreshed on a schedule satisfies freshness at the refresh interval but fails arrival (its $N ( t )$ has epochs) and fails rating staleness between refreshes. A platform that records tasks continuously but executes them in nightly batches satisfies arrival and may satisfy contamination resistance, but fails execution contemporaneity, and its judgments compare runs made under conditions that may difer from the submitter’s. A platform that updates a streaming rating but publishes a snapshot blended with a fixed benchmark score fails rating staleness for the published number, because the blended component moves only when the snapshot is rebuilt.

## 5 Rating Methodology

## 5.1 Pairwise comparison model

Each agent a has a latent strength $\theta _ { a } \in \mathbb { R } ;$ ; write $\theta = ( \theta _ { 1 } , \ldots , \theta _ { m } )$ . Under the Bradley-Terry model [2, 31] the probability that agent i is preferred to agent j in a comparison is

$$
p _ {i j} = \mathbb {P} \{i \succ j \} = \frac {e ^ {\theta_ {i}}}{e ^ {\theta_ {i}} + e ^ {\theta_ {j}}} = \sigma (\theta_ {i} - \theta_ {j}), \quad \sigma (x) = \frac {1}{1 + e ^ {- x}}.\tag{16}
$$

Only diferences of strengths are identified; adding a constant to every $\theta _ { a }$ leaves every $p _ { i j }$ unchanged. Ratings are reported on the Elo scale by the afine map

$$
R _ {a} = R _ {0} + \frac {4 0 0}{\ln 1 0} \theta_ {a} \approx R _ {0} + 1 7 3. 7 2 \theta_ {a},\tag{17}
$$

with origin $R _ { 0 } = 1 0 0 0$ , so that a diference of 400 Elo points corresponds to odds of 10 to 1, as in [8].

## 5.2 Observations, ties, and weights

A rated battle b between agents $i _ { b }$ and $j _ { b }$ yields an outcome $y _ { b } \in \{ 1 , \frac { 1 } { 2 } , 0 \} \colon 1$ if $i _ { b }$ was preferred, 0 if $j _ { b }$ was, and $\textstyle { \frac { 1 } { 2 } }$ for a tie. We treat a tie as half a win for each side, the standard approximation that keeps the likelihood in the binomial family; the alternative of a tie parameter [5, 25] adds one parameter and is appropriate when ties are frequent enough to estimate it. A judgment of “both unacceptable” is recorded as a distinct label, because it is a statement about quality, and enters the rating as a tie, because it carries no preference between the two.

Each battle carries an evidence weight $w _ { b } \in ( 0 , 1 ]$ (Section 5.5), and the log-likelihood of the parameters given n rated battles is

$$
\mathcal {L} (\theta) = \sum_ {b = 1} ^ {n} w _ {b} \Big [ y _ {b} \log \sigma (\theta_ {i _ {b}} - \theta_ {j _ {b}}) + (1 - y _ {b}) \log \big (1 - \sigma (\theta_ {i _ {b}} - \theta_ {j _ {b}}) \big) \Big ].\tag{18}
$$

A battle judged by several people enters (18) once, with the consensus outcome of Section 6.4, not once per judge; otherwise a redundancy sample meant to measure noise would triple that battle’s weight.

## 5.3 Penalized maximum-likelihood estimator

Ford’s condition [10] governs whether the unpenalized estimate exists at all: every agent must be joined to every other by both a chain of wins and a chain of losses. Early in an arena that fails routinely, because an agent that has not yet lost, or not yet won, drives its own estimate of to infinity. We therefore maximize a ridge-penalized objective,

$$
\hat {\theta} = \arg \max _ {\theta} \mathcal {L} (\theta) - \frac {r}{2} \| \theta \| _ {2} ^ {2},\tag{19}
$$

with a small penalty $r > 0$ (we use $r = 1 0 ^ { - 3 } )$ , which pins the shift and keeps a separated agent finite. The penalty is disclosed as part of the published method because it shrinks toward the origin.

Writing $x _ { b } \in \mathbb { R } ^ { m }$ for the design vector of battle b (+1 at $i _ { b } , - 1$ at $j _ { b } , 0$ elsewhere), $\eta _ { b } = x _ { b } ^ { \top } \theta$ and $\mu _ { b } = \sigma ( \eta _ { b } )$ , the gradient and negative Hessian of the objective are

$$
g (\theta) = \sum_ {b} w _ {b} (y _ {b} - \mu_ {b}) x _ {b} - r \theta , H (\theta) = \sum_ {b} w _ {b} \mu_ {b} (1 - \mu_ {b}) x _ {b} x _ {b} ^ {\top} + r I.\tag{20}
$$

We solve (19) by Newton steps, $\theta  \theta + H ( \theta ) ^ { - 1 } g ( \theta )$ , stopping once no coordinate moves by more than a tolerance (Algorithm 2). Strict concavity of the penalized objective guarantees convergence from the zero start. After convergence we center the estimate on the mean strength of the agents that have reached the provisional floor of Section 5.7, so that a newcomer’s first, poorly identified estimate does not move every incumbent’s published number.

## 5.4 Streaming update

When a single judgment resolves battle b at time $h _ { b }$ , the streaming estimator takes one stochasticgradient step on that battle’s term of (18):

$$
\theta_ {i _ {b}} \leftarrow \theta_ {i _ {b}} + \eta_ {i _ {b}} w _ {b} (y _ {b} - \mu_ {b}), \qquad \theta_ {j _ {b}} \leftarrow \theta_ {j _ {b}} - \eta_ {j _ {b}} w _ {b} (y _ {b} - \mu_ {b}),\tag{21}
$$

with per-agent step sizes $\eta _ { a }$ . Mapping to the Elo scale by (17) and setting $\eta _ { a } = K _ { a }$ ln 10/400 gives

$$
R _ {i _ {b}} \leftarrow R _ {i _ {b}} + K _ {i _ {b}} w _ {b} (y _ {b} - \mu_ {b}), \quad \mu_ {b} = \frac {1}{1 + 1 0 ^ {(R _ {j _ {b}} - R _ {i _ {b}}) / 4 0 0}},\tag{22}
$$

which is the Elo update [8] with a per-side factor $K _ { a }$ . The streaming estimator is thus a first-order online method for the same model the refit solves exactly, and the two disagree only by the path dependence of the online method. We use a factor that decays with the agent’s rated-battle count $n _ { a }$

$$
K (n _ {a}) = K _ {\mathrm{min}} + (K _ {\mathrm{max}} - K _ {\mathrm{min}}) \frac {n _ {0}}{n _ {0} + n _ {a}},\tag{23}
$$

with $K _ { \mathrm { m a x } } = 4 8 , K _ { \mathrm { m i n } } = 1 2$ , and $n _ { 0 } = 3 0 $ , so that a new agent moves quickly and a settled agent slowly (Algorithm 1). The streaming value is displayed beside the refit and labeled, because it is what changes when a judge votes, but the refit is the published rating, for the reasons given in Section 4.4.

## 5.5 Admissibility and evidence weight

Not every judged battle enters (18). A battle is excluded, in this order, when: the judge-visible text named a model (the vote was not blind); one side has no run record; one side produced no trajectory (an upstream outage, not a performance); the submitter ended one side early; the two sides ran under diferent step budgets; or no admissible vote remains once retracted votes, votes by judges marked untrusted, and votes recorded in less time than the two results take to read are removed. Every exclusion is counted and published beside the rating.

Among admissible votes on a battle, votes by judges other than the submitter take precedence: if any independent judge voted, the submitter’s own vote is dropped from that battle’s consensus; if none has, the submitter’s blind vote decides and the battle is counted in a published “self-judged only” tally. The evidence weight is

$$
w _ {b} = \gamma_ {b} \cdot \bar {\omega} _ {b}, \quad \gamma_ {b} \in \{\gamma_ {\mathrm{cal}}, 1 \}, \quad \bar {\omega} _ {b} = \frac {1}{| V _ {b} |} \sum_ {v \in V _ {b}} \omega_ {v} \in [ \omega_ {\min}, 1 ],\tag{24}
$$

where $\gamma _ { \mathrm { c a l } } = 0 . 2 5$ discounts a battle whose pairing was a new submitter’s calibration showcase (a pairing shaped by an input the matchmaker otherwise never sees), $V _ { b }$ is the set of judges whose votes produced the consensus outcome, and $\omega _ { v } \in [ \omega _ { \operatorname* { m i n } } , 1 ]$ is judge v’s graded trust weight (Section 6.4), floored at $\omega _ { \mathrm { m i n } } = 0 . 1$ so that a graded signal discounts but never silences.

## 5.6 Confidence intervals

Model-based. At the optimum, $H ( { \hat { \theta } } )$ from (20) is the observed information. Because the likelihood does not identify the shift, the covariance of the centered parameters is obtained by projecting out the all-ones direction: with $\begin{array} { r } { P = I - \frac { 1 } { m } \mathbf { 1 } \mathbf { 1 } ^ { \top } } \end{array}$ ，

$$
\widehat {\mathrm{Cov}} (\hat {\theta}) = P H (\hat {\theta}) ^ {- 1} P, \qquad \mathrm{SE} (\hat {\theta} _ {a}) = \sqrt {\widehat {\mathrm{Cov}} _ {a a}}, \qquad \mathrm{CI} _ {9 5} (R _ {a}) = \hat {R} _ {a} \pm 1. 9 6 \cdot \frac {4 0 0}{\ln 1 0} \mathrm{SE} (\hat {\theta} _ {a}).\tag{25}
$$

Without the projection, the shift direction contributes a variance of $1 / ( m r )$ to every diagonal entry, which for $r = 1 0 ^ { - 3 }$ and $m = 5$ is 200 in θ units: a spurious interval thousands of Elo points wide. The projection removes exactly that component.

Cluster-robust. Votes are not independent draws: one judge casts many of them, and a judge’s leanings are shared across their votes. We therefore publish a sandwich estimator [21, 28] clustered on the judge,

$$
\widehat {\mathrm{Cov}} _ {\mathrm{CR}} (\widehat {\theta}) = \frac {G}{G - 1} H ^ {- 1} \Bigl (\sum_ {g = 1} ^ {G} u _ {g} u _ {g} ^ {\top} \Bigr) H ^ {- 1}, \qquad u _ {g} = \sum_ {b \in g} w _ {b} (y _ {b} - \mu_ {b}) x _ {b},\tag{26}
$$

where $g$ indexes the G distinct judges whose votes decided battles and $u _ { g }$ is the summed score of cluster $g .$ . The score vectors satisfy $\mathbf { 1 } ^ { \top } x _ { b } = 0$ , so the sandwich has no shift component and needs no projection. The estimator is identified only when $G$ exceeds the number of parameters; when it does not, no interval is published rather than a spuriously narrow one. Clustering on the judge is the correct choice for an arena in which each task is submitted once; clustering on the task would place one observation in every cluster and reproduce the naive standard errors.

Rank bands. A rank is not a parameter, and its uncertainty is not a symmetric interval. We publish for each agent the 95% band of positions it holds when every rating is drawn from its own normal approximation and the field is re-ranked, together with the share of draws in which it was first (Algorithm 3). Draws are seeded per agent so that the same corpus yields the same band and adding an agent does not change another agent’s draws. The band uses each agent’s marginal variance and ignores the of-diagonal covariance; this errs toward wider bands, which is the safe direction for a published ordering.

## 5.7 Entry of a new agent

A new agent enters the roster with no rating. Until it has $n _ { 0 } = 3 0 $ rated battles it is provisional: the refit’s estimate for it is withheld from the board, because a record with no loss, or no win, is separated and its estimate is determined by the penalty rather than by data; the streaming value is shown instead with an interval of the full scale, labeled as the streaming value. The matchmaker samples the newcomer with weight $( n _ { a } + \kappa ) ^ { - 1 / 2 } , \kappa = 4$ , so its exposure converges to the field’s. Once the floor is reached, the fitted rating, its interval, and its rank band are published. The agent is never given a seed rating that asserts it is average: its published number is whatever its record implies.

## 5.8 Convergence

Consider two agents that play only each other, n times, with true preference probability $p .$ The information about $\theta _ { i } - \theta _ { j }$ per game is $\textstyle p ( 1 - p ) \leq { \frac { 1 } { 4 } }$ , so the standard error of the estimated diference satisfies 2

$$
\mathrm{SE} (\hat {\theta} _ {i} - \hat {\theta} _ {j}) = \frac {1}{\sqrt {n p (1 - p)}} \geq \frac {2}{\sqrt {n}},\tag{27}
$$

with equality at $\begin{array} { r } { p = \frac { 1 } { 2 } } \end{array}$ . On the Elo scale the 95% half-width is at least $1 . 9 6 \times 1 7 3 . 7 2 \times 2 / \sqrt { n } \approx$ $6 8 1 / { \sqrt { n } } ;$ : about 68 points after 100 games and about 22 points after 1,000. This is why the matchmaker prefers pairs near parity: a comparison at $p = 0 . 9$ carries 0.09 units of information against 0.25 at $p = 0 . 5$ , roughly a third as much for the same cost in sandbox minutes and judge attention. In a field of m agents the standard error of a centered strength also depends on the connectivity of the comparison graph; Figure 3 shows the empirical behavior in a simulation.

## 6.4 Vote quality

Consensus on a battle. When several judges vote on one battle, the outcome entering (18) is the plurality choice, with the rule that a side wins only if it out-polls both the other side and the non-preferences (ties and “both unacceptable”) combined; otherwise the battle is a tie. One vote per person is counted, the earliest, so that a judge who voted under two identities does not carry a majority alone.

Abstentions. A judge may decline to judge a battle. An abstention is recorded with its reason, releases the judge’s hold so the battle returns to the queue, and does not enter the likelihood or the agreement statistics. Abstention rates are published per reason because a high rate on a class of tasks is information about the tasks.

Agreement. Agreement is measured on the redundancy sample, the battles assigned three judges at creation. Drawing the sample at creation rather than at judging time is deliberate: a sample of battles that happened to attract several judges would over-represent short, recent, popular tasks. For two judges we report Cohen’s κ [4]; for the three-judge sample we report

Judge trust. Each judge carries a graded weight $\omega _ { v } \in [ \omega _ { \operatorname* { m i n } } , 1 ]$ computed from two behaviors that cannot be opinions. The first is a position lean: the lower bound of a Wilson interval on the judge’s share of votes for the left-hand side, when that interval excludes one half. Sides are shufled per battle, so position carries no information. The second is a habit of voting faster than the two results could have been read: the lower bound of a Wilson interval on the share of the judge’s timed votes that fall under a reading-rate floor. Both factors are 1 below their evidence floors; the product is clamped to $[ \omega _ { \mathrm { m i n } } , 1 ]$ . A judge is marked untrusted, and their votes dropped rather than discounted, only by thresholded evidence: failing gold-standard items with known outcomes, or an accuracy on an elimination task below a chance-corrected floor over enough calls. The number of discounted judges, the number of dropped votes, and the share of the corpus that rests on self-judged battles are published beside the ratings.

## 7 Limitations

Human latency is not bounded by the system. Definition 4.1 excludes $J _ { b }$ on purpose, and the illustrative timeline of Figure 2 makes it the dominant term. An arena can shorten $J _ { b }$ by prioritizing the queue and by recruiting judges; it cannot guarantee a bound. A reader who needs a bound on end-to-end latency should read the reported percentile of $J _ { b }$ , not the machine horizon.

Judge population and self-judging. In a young arena most judgments come from a small number of people, and a large share of battles are judged only by their own submitter. Blinding is enforced by the server for the submitter as for anyone else, so those votes are real blind labels; what they carry is annotator concentration, which the cluster-robust interval widens to reflect and which the published self-judged share makes visible. The intervals are honest about this; the point estimates are still one population’s preferences.

Task population. The tasks are whatever users submit. That is the property that makes the evaluation track use, and it is also a selection efect that no reweighting in this paper corrects. The published distribution over task categories is descriptive; a ranking on it does not transfer to a workload with a diferent mix.

Figure 5: Failure-to-environment pipeline. A failed run is captured with its trajectory and initial snapshot, redacted, synthesized into an environment triple (initial state, instruction, grader), validated by replaying the failing trajectory and a reference, and published to a registry. Three things follow from the figure: the feedback latency is a sum of five bounded stages, that validation is the dominant and run-length-dependent term, and that an environment which cannot reproduce its own failure is rejected rather than published.

Ties as half-wins. The half-win treatment is an approximation. With ties at roughly one vote in seven, as in the worked example (29 of 211), a tie-parameter model [5, 25] would be estimable and would change the intervals; we have not quantified the diference here.

Marginal rank bands. The rank band uses each rating’s marginal variance and ignores the covariance the fit also estimates. The approximation errs toward wider bands, and the direction is stated, but a joint draw from the full covariance would be more accurate.

## 8 Conclusion

We have described an arena for computer-use agents and multi-agent systems in which real tasks are executed by two entrants at once in identical isolated environments, judged blind, and turned into a leaderboard. We have defined what it means for that evaluation to be real-time as five measurable properties: continuous arrival, live concurrent execution, online rating updates, freshness with contamination resistance, and bounded feedback latency to a training environment. Each property has a quantity a deployed system can report at a percentile, and Definition 4.1 names the tier at which each holds. The rating methodology is a penalized Bradley-Terry fit with cluster-robust intervals and bootstrap rank bands, with a streaming Elo update shown to be a first-order online step on the same likelihood. The worked example shows that a few hundred votes separate the ends of a five-agent field and leave neighbors overlapping, which is the honest state of many leaderboards and the reason a rank should be published as a band. The definitions are ofered so that the word real-time, when applied to an evaluation, can be checked rather than believed.

## C.6 One battle, end to end

The following walks one battle through the system with the illustrative event times of Figure 2 and the ratings of Table 2. The two agents drawn are A and B.

1. Submission $( s _ { b } = 0 )$ . A user submits the first task of Table 4. Intake authenticates the user, confirms consent, classifies the text as a task, finds no near-duplicate among the user’s recent tasks, and admits it. Elapsed: under one second.

2. Matchmaking and dequeue $\left( q _ { b } = 5 \mathrm { ~ s } \right)$ . The sampler draws Agents A and B. With 86 and 87 rated battles they are the two agents with the most accumulated evidence, and the pairing is informative: $\sigma ( \hat { \theta } _ { A } - \hat { \theta } _ { B } ) = \sigma ( 0 . 8 0 4 - 0 . 2 8 8 ) = 0 . 6 2 6$ is well inside the range where a comparison carries information. The battle waits 5 s for an execution slot.

3. Provisioning and lane start $( q _ { b } + \delta _ { b } = 4 5 \mathrm { ~ s ) }$ . Two isolated desktops are provisioned. Both lanes receive the same instruction, the same tool schemas, the same step budget K and wall-clock budget W, and start within the skew bound.

4. Execution $( e _ { b } = 6 \mathrm { ~ m i n ~ } 4 5 \mathrm { ~ s } )$ . Agent A finds a nonstop fare and stops before payment; Agent B selects a one-stop fare and reaches the payment page. Both runs end within the budgets. Every step’s screenshot and action are recorded for both.

5. Judging $( h _ { b } = 3$ h 6 min 45 s). The battle was drawn for redundancy at creation, so it collects three judges. The first arrives after about three hours (illustrative) and votes for the left-hand run, which is Agent A. The two later judges also vote A; the consensus is A with three agreeing judges, and the battle contributes $P _ { i } = 1$ to the agreement statistic of Section 6.4.

6. Streaming update (within milliseconds of the first vote). Before the vote, $R _ { A }$ = 1139.7 and $R _ { B } = 1 0 5 0 . 0 \ \AA$ . By equation (22), the expected score of A is $\mu = 1 / ( 1 +$ $1 0 ^ { ( 1 0 5 0 . 0 - 1 1 3 9 . 7 ) / 4 0 0 } ) = 1 / ( 1 + 1 0 ^ { - 0 . 2 2 4 3 } ) = 0 . 6 2 6 3$ . The factors from equation (23) are $K _ { A } = 1 2 + 3 6 \cdot 3 0 / ( 3 0 + 8 6 ) = 2 1 . 3 1$ and $K _ { B } = 1 2 + 3 6 \cdot 3 0 / ( 3 0 + 8 7 ) = 2 1 . 2 3$ . With $y _ { b } = 1$ and $w _ { b } = 1 , \mathrm { ~ A ~ }$ gains $K _ { A } ( 1 - \mu ) = 7 . 9 6$ points and B loses $K _ { B } ( 1 - \mu ) = 7 . 9 3 $ points: the streaming values become $R _ { A } = 1 1 4 7 . 7$ and $R _ { B } = 1 0 4 2 . 1$ . The judge sees these move at once, labeled as the streaming value.

7. Refit (within 31 s of the vote). The next periodic refit runs Algorithm 2 on the 212 admissible battles. Adding one A-over-B outcome to the 211 of Table 2 moves the centered estimates to $R _ { A } = 1 1 4 2 . 6$ (a change of +2.9) and $R _ { B } = 1 0 4 7 . 5$ (a change of −2.5); the interval half-widths change by less than one Elo point. The published rating and its band are recomputed from this fit, and the board that clients poll reflects the vote with staleness under 31 s.

8. Feedback $( \nu _ { u } \approx e _ { b } + 2 2$ min, in parallel with judging). Agent B’s run ended with a constraint violation, so the pipeline of Section 4.6 captured, redacted, synthesized, validated and published the environment record of Figure 9 about 22 minutes after the run ended, well before the first judge arrived. This was possible because the failure was a constraint violation a checker can detect without a judgment, so the grader was derived from the constraint and the left-hand run served as the mechanical reference; a wrong-result failure whose grader needs the judged-correct run waits for the judgment.

Two things in this walk-through are the point of the paper. The streaming update and the refit agree in direction and difer in magnitude, because one is a single first-order step and the other re-solves the whole likelihood; the board publishes the second and shows the first. And the machine stages, from submission to a published refit, total about seven minutes plus 31 s, while the human stage took three hours: the system can bound what it controls, and it reports what it does not.
